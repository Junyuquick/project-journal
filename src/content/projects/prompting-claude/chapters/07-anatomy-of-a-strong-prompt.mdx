## The order that works

1. The task and the role.
2. Background documents and data.
3. Detailed step-by-step instructions.
4. Examples.
5. The immediate task.
6. The output format you want.
7. A short reminder of what matters most.

## Ten rules of thumb

1. **Set context first.** With no context, Claude guesses.
2. **Put stable background in one place**, such as a system prompt or [CLAUDE.md](glossary:claude-md).
3. **Use structure**: XML tags or clear headings like `<instructions>`, `<context>`, `<examples>`.
4. **Give 3 to 5 relevant, varied examples.** They are among the most reliable ways to steer.
5. **Say what to do, not what to avoid.** "Write flowing prose paragraphs" beats "no markdown".
6. **Give the reason behind a rule.** Claude generalises from reasons.
7. **Define the output format.**
8. **Allow "I don't know"**, so it says so instead of guessing.
9. **Iterate.** Prompting is test and refine, not one shot.
10. **Long documents first, the question last.**

## Notes for the current model (Sonnet 5.5)

- Use `medium` effort for well-specified coding work and `high` for harder or longer jobs. At lower effort it may stop to check in, or skip verification. A higher effort level, or "keep going until the check passes", fixes that.
- It tends to add tests and docs that fit your repo. If you want only the requested change, say: "only make the requested changes; no extra files or refactors."
- If it says "done" with no test output, tell it to run the tests and show the result.
- "Can you suggest changes?" may get only suggestions. Say "make these changes."
