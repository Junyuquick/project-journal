A **check** is anything Claude can run and read: [tests](glossary:test), a [build](glossary:build) that succeeds or fails, a linter, or a screenshot compared with a design. With a check, Claude can try, see that it failed, and fix it by itself. Without one, you have to be the person who tests everything.

## Weak and strong, side by side

| Weak | Strong |
|---|---|
| "implement email validation" | "write validateEmail. Cases: user@example.com is true, invalid is false, user@.com is false. Run the tests after." |
| "make the dashboard look better" | "[paste screenshot] implement this design, take a screenshot of the result, list the differences, and fix them" |
| "the build is failing" | "build fails with: [paste the error]. Fix it, check the build passes, fix the root cause, and do not hide the error" |

Notice what the strong versions share: they say what "right" looks like and they tell Claude to go and look.

## Ask for evidence

When Claude says "done", ask to see the test output, the command it ran or the screenshot. "It works" is a claim. Output is evidence. This is the same idea behind test-driven work, where the [test](glossary:tdd) comes first and the code is written to satisfy it.
