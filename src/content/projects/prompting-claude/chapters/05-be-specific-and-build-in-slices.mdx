## Be specific

Vague prompts are fine for exploring ("what would you improve in this file?"). For real work, be exact:

- **Scope.** Which file, which scenario, what testing style ("avoid mocks").
- **Sources.** Point to `@file`, paste URLs, images or logs.
- **Patterns.** "Follow how HotDogWidget.php does it."
- **Symptoms.** Say what you see, where you think it is, and what "fixed" means.

## Build in vertical slices

A very long prompt for a whole app gives worse results than building piece by piece. The order that works:

1. Set up a skeleton and deploy it.
2. Build one [vertical slice](glossary:vertical-slice): one feature, end to end.
3. Give that slice its own check.
4. Make it small enough to [commit](glossary:commit).
5. Repeat.

Treat version one as an [MVP](glossary:mvp): the smallest thing that does the main job.

## Across many sessions

For a build that spans several sessions, the first session sets up the framework: tests, a script that starts the project, and a progress file. Later sessions work through a to-do list. Use [git](glossary:git) as the memory, and start fresh sessions instead of relying on one that has grown huge. And never let Claude delete or edit tests just to make them pass.
