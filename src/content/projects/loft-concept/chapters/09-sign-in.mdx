When the client clicks Save, the admin writes to GitHub on their behalf. GitHub must know who is asking and that they are allowed. That is the job of signing in.

## OAuth in one picture

[OAuth](glossary:oauth) lets the admin act on the client's behalf at GitHub without ever seeing their GitHub password. The client types their password only on GitHub's own page, and the admin receives a limited key (a token) in return.

## Why a Worker is needed at all

The last step, swapping the one-time code for a token, needs a **client secret**: a password that proves the request really comes from our app. Anything inside a web page can be read by anyone who opens it, so the secret cannot live in the admin page. It must live on a server.

The site has no server; that is the point of a static site. So a tiny program, a [Cloudflare Worker](glossary:cloudflare-worker), does just this one job. It runs on Cloudflare's free plan, and your domain and hosting stay with Vodien. You asked about that directly: Cloudflare hosts nothing for the website and does not touch the domain.

## What you set up

This part had to be done in your own accounts, so you did it with Claude guiding:

1. **Deployed the Worker** with Sveltia's "Deploy to Cloudflare" button. This created a copy of its code on your GitHub account and the Worker at `sveltia-cms-auth.junyuquick246.workers.dev`. Using your account (not the client's) keeps the infrastructure with the developer.
2. **Registered a GitHub OAuth app** called Loft Concept Admin, whose callback address is the Worker's `/callback`. That tells GitHub where to send people after they approve.
3. **Gave the Worker its settings**: the Client ID, the client secret (stored encrypted) and `ALLOWED_DOMAINS` set to the live and staging addresses, so other websites cannot use your Worker.

Claude then added the Worker's address to the admin config as `base_url`, test first.

## Why expiring tokens were turned off

GitHub's form had "Expire user access tokens" ticked by default. Claude read the Worker's code and found it does not pass on GitHub's refresh token, the thing that renews an expired one. With expiry on, the client's session would have broken after about 8 hours with an error. With it off, they stay signed in, and access can still be removed at any time by taking them off the repository.

## The settings mix-up, solved together

After setup, Claude tested the Worker directly and it answered: "OAuth app client ID or secret is not configured", with an empty list of allowed domains. None of the settings had reached it.

Your screenshot showed why: there was a single variable whose **name** was the Client ID itself, instead of a variable named `GITHUB_CLIENT_ID` holding that ID as its **value**. You deleted it, added the three variables properly and redeployed. Claude re-tested: both your domains were now sent to GitHub's login, and a made-up domain was refused (`UNSUPPORTED_DOMAIN`).

## Signing in is not the same as being allowed

Anyone with a GitHub account can sign in. But saving means writing to the repository, and GitHub only allows that for collaborators. The repository has two: you, and the client's account `loftconcept`, which you created and added. A stranger can sign in and see the admin, but every save would be refused.
