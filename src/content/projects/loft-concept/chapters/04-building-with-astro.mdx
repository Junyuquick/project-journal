The old site was written by hand: every page was a complete HTML file, so the header and footer existed 25 times. Change the menu, and you had to change 25 files and hope you did not miss one. [Astro](glossary:astro) removes that problem.

## What Astro does

Astro is a static site generator. You write the site as reusable pieces, and when you run a [build](glossary:build), Astro assembles them into ordinary [HTML](glossary:html) files. Visitors never run Astro; they just receive the finished pages.

## Components and one layout

A [component](glossary:component) is a reusable piece of a page, saved in its own `.astro` file: the header, the footer, a project card, a photo, the booking call to action. A **layout** is the frame every page shares. Each page then only contains what is unique to it.

So the header now exists once, in `Header.astro`. Fixing a menu link means editing one file, and all pages get the fix at the next build.

## Projects as a content collection

The biggest change was the 19 project pages. Each one became a small [Markdown](glossary:markdown) file holding only the project's facts, at the top in a block called front matter:

```yaml
---
title: "Bedok Road"
sector: residential
summary: "Luxury distilled into every surface. A double-height kitchen..."
cover: "../../assets/projects/bedok-road/01-20151026-147bedokroad-110.jpg"
gallery:
  - "../../assets/projects/bedok-road/02-20151026-147bedokroad-116.jpg"
featured: false
order: 2
---
```

Together these files form a [content collection](glossary:content-collection). One template, `src/pages/portfolio/[slug].astro`, turns each file into a page. The square brackets mean "make one page for every project", so `bedok-road.md` becomes `/portfolio/bedok-road`.

This decision paid off later in a way nobody planned for at the time: because projects are just files with known fields, the client admin (LC08) could be a simple form that edits those files.

## A schema guards the files

Every project file is checked against a [schema](glossary:schema), a description of the fields a project must have:

```ts
z.object({
  title: z.string(),                                  // text, required
  sector: z.enum(['residential', 'commercial']),      // one of two values
  summary: z.string().min(20),                        // at least 20 characters
  cover: image(),                                     // a real image file
  gallery: z.array(image()).default([]),              // a list of images, may be empty
  order: z.number().int(),                            // a whole number
})
```

Plain English: `z.string()` means "must be text", `.min(20)` means "at least 20 characters", and `image()` means "must point at an image file that exists". If a file breaks a rule, the build stops with a message naming the file and the field. A mistake cannot reach the live site.

## The other pages

The same approach built the rest: the home page (hero video, statement, selected work, sector panels, process, a testimonial, booking), the portfolio index with a residential/commercial filter that still works without JavaScript, about, testimonials, and a contact form with plain-language error messages. Each page is mostly a short list of components in order.
